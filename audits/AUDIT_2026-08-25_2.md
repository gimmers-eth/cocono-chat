# Security Audit (Round 2) — cocono-chat

- **Date:** 2026-08-25
- **Scope:** Independent verification that all 20 findings of
  [AUDIT_2026-08-25](./AUDIT_2026-08-25.md) are actually fixed, plus a fresh pass over
  the changed code for newly introduced issues.
- **Method:** The fixes were **not taken at face value**. Every finding was re-checked
  against the current source; security-critical ones were re-tested empirically:
  - Live `app.inject()` probes of the rebuilt admin gate (percent-encoding bypass
    attempts, token brute-force throttling), replicating `be/src/admin.js` exactly with
    the real admin routes registered.
  - Live probes of the main app (security headers, log redaction, budget-drain attack).
  - Boot-behavior probes (`pnpm start` without a real JWT secret; admin non-loopback
    bind without `ADMIN_TOKEN`).
  - Full test suite re-run; `pnpm audit` re-run.

## Verdict

**19 of 20 original findings are fully fixed and verified.** One finding — **M1
(targeted login DoS)** — is only partially fixed: the reported junk-nonce vector is
closed, but an empirically proven residual vector remains (see [N1](#n1--residual-of-m1-targeted-login-dos-via-self-requested-nonces)).
Three minor new items were also found ([N2](#n2--trust_proxytrue-trusts-any-x-forwarded-for)-[N4](#n4--pre-fix-identities-still-carry-aesraw-in-indexeddb));
none are high severity.

## New / residual findings

### N1 — Residual of M1: targeted login DoS via self-requested nonces

**Severity: Medium** (same impact class as the original M1; attack cost doubled)
**Location:** `be/src/routes/app-routes/auth.js` (verify), enabled by the L1 fix in
challenge.

The M1 fix reorders verify to consume the nonce **before** counting against the
account's `rl:verify:<ul>` budget — so junk requests with *invalid* nonces no longer
count (the regression test covers exactly this). But an attacker can request **valid**
nonces at will: since the L1 fix, `/api/auth/challenge` issues a nonce for *any*
(username, device) pair, including device ids that are not registered on the account.
Such a nonce passes verify's nonce check, and the request then increments the victim's
account budget before failing signature verification (the attacker's device id is not
on the account → `bad_signature`).

**Proven empirically** (probe against `buildApp` with `verifyAccountLimit: 5`,
`verifyIpLimit: 100`, `challengeIpLimit: 1000`):

```text
loop: challenge({u: victim, d: attacker-fake-device-i}) -> 200 nonce
      verify({u: victim, d: attacker-fake-device-i, n, s: garbage}) -> 401 bad_signature
      ... 5 iterations consume the whole budget ...
victim's real login afterwards -> 429 (locked out for the rest of the window)
```

With the shipped defaults (`VERIFY_ACCOUNT_LIMIT=20`, `VERIFY_IP_LIMIT=20`,
`CHALLENGE_IP_LIMIT=30` — all per 15 min), a **single IP** can exhaust a victim's
budget: each unit costs one challenge + one verify (20 ≤ both IP limits), after which
the victim's legitimate logins receive 429 for up to 15 minutes, repeatable every
window. The per-IP verify limit added in the fix does not protect against this because
it is equal to the account budget.

**Recommended fixes (pick one):**
1. **Count only real attempts:** move the `rl:verify:<ul>` increment to *after* device
   resolution — i.e. only count attempts against a device actually registered on the
   account. Attempts against unregistered device ids (the attacker's case) then hit only
   the IP-based limiters, and the victim's budget is spent only on attempts that matter.
   (Brute-force protection is unaffected: Ed25519 signatures cannot be brute-forced.)
2. Set `VERIFY_IP_LIMIT` substantially lower than `VERIFY_ACCOUNT_LIMIT` so one IP
   cannot exhaust a budget alone (weaker: distributed attackers still can).

Also worth a regression test for this exact vector (the current M1 test only sends
invalid nonces).

### N2 — `TRUST_PROXY=true` trusts any `X-Forwarded-For`

**Severity: Low**
**Location:** `be/src/config.js` (`parseTrustProxy`), `be/.env.example`

`TRUST_PROXY=true` makes Fastify trust the first `X-Forwarded-For` value unconditionally.
If the app port were ever reachable directly (bypassing nginx), attackers could spoof
`request.ip` and evade every per-IP rate limit (or frame other IPs into limits).
`.env.example` currently documents `true` as the first option without this caveat.

**Fix:** In `.env.example`, recommend a hop count or explicit trusted addresses for
production (nginx sets the header; only the proxy hop should be trusted), and note that
`true` is only safe when the port is unreachable except through the proxy. Optionally
warn at boot when `trustProxy === true`.

### N3 — Signature de-dup is marked before the write side effect

**Severity: Informational**
**Location:** `be/src/routes/app-routes/signup.js`, `devices.js` (`isReplayedSignature`
runs after signature verification but before the Mongo write)

If two concurrent requests carry the *same* valid signed payload, the loser gets
`401 replay` rather than a meaningful result (`409 username_taken` etc.). The shipped
FE is unaffected — it regenerates `t` and the signature on every attempt — but any
future/third-party client that retries with a byte-identical payload will see this.
Document it in the OpenAPI note on replay, or mark `sigseen` only after the write
succeeds (accepting a tiny double-write race that the unique index already resolves).

### N4 — Pre-fix identities still carry `aesRaw` in IndexedDB

**Severity: Low**
**Location:** `fe/js/db.js` / `fe/js/app.js`

The M3 fix stops *writing* `aesRaw`, but identity records saved by pre-fix versions
still contain the raw AES bytes — `saveIdentity` is only called on signup/enroll, never
on login, so old records are never rewritten. The field is dead weight (nothing reads
it) but remains readable same-origin.

**Fix:** On `getIdentity()` load (in `init()`), if the record has `aesRaw`, delete the
field and re-save. One-time migration that completes M3 for existing users.

## Assessment of the fix quality

The remediation was thorough and well-executed:

- Fixes match the recommended approaches (encapsulated gate, boot refusal, atomic
  limiter, `SET NX` claims, registry-based revocation, timestamp + de-dup freshness).
- No regressions: full suite green; docs (DESIGN.md, OpenAPI, READMEs, `.env.example`)
  were kept consistent with the code.
- Honest status-keeping: the round-1 doc's "Outstanding items" correctly distinguishes
  code fixes from deployment tasks and accepted trade-offs (L1 signup/enroll, L7).
- The one miss (N1) is a second-order effect: the L1 uniformity fix and the M1 reorder
  are each individually correct, but their combination keeps a slower version of the
  original DoS open — the kind of interaction worth a dedicated regression test.
