# Security Audit — cocono-chat

- **Date:** 2026-08-25
- **Scope:** Full manual source review of the current codebase (milestones 1–2: accounts +
  multi-device): backend (`be/src/`), admin app (`be/src/admin.js`, `be/admin/`), frontend
  (`fe/`), configuration (`be/src/config.js`, `be/.env.example`), and dependency state
  (`pnpm audit`). WebSocket/messaging layers do not exist yet and are out of scope.
- **Method:** Line-by-line review of auth/crypto/routes/config code, cross-checked against
  DESIGN.md and the OpenAPI spec; `pnpm audit` for dependency advisories; empirical probing
  of router/gate behavior with `app.inject()` (Fastify's router decodes percent-encoded
  paths while `request.url` stays raw — confirmed with find-my-way 9.9.0 sources and a
  live probe).

## Remediation status (updated 2026-08-25)

All 4 High, all 7 Medium, and all 9 Low findings have been addressed. Each finding below
carries a **Status** line and a **Fix** description. See
[Outstanding items](#outstanding-items--follow-ups) for what deliberately remains.

**Verification performed after the fixes:**
- Test suite: 31/31 passing (6 new regression tests added for H4, M1, M6, L1, L6, replay).
- `pnpm audit`: **no known vulnerabilities** (was 4 advisories on `@fastify/static@8.3.0`).
- Live probes: H1 bypass attempt (`/%61pi/admin/users`) now 401; static path-traversal
  probes blocked with zero secret bytes leaked; M7 non-loopback boot refusal reproduced;
  M5 capability confirmed absent from logs; M4 CSP present; H2 boot refusal reproduced;
  L6 confirm-dialog flow exercised in a real browser.

## High

### H1 — Admin token gate bypassed by percent-encoded paths (verified)

**Status: ✅ FIXED** — `be/src/admin.js`. The token gate was moved **inside the admin
routes' encapsulation scope** (`app.register(async instance => { instance.addHook(...);
instance.register(adminRoutes, ...) })`), so it keys off the *matched route* rather than
the raw request URL. Percent-encoding the path no longer changes whether the gate runs.
Also added: constant-time token comparison, and per-IP throttling of failed token
attempts (`rl:admintoken:<ip>`).

**Fix verified live:** `GET /%61pi/admin/users` without token → **401** (previously 200);
with the correct token → 200 (routing still works, gate still enforced).

<details>
<summary>Original finding</summary>

**Location:** `be/src/admin.js:17-21`

The admin app gates its API with an `onRequest` hook that checks the **raw** request URL:

```javascript
if (!request.url.startsWith('/api/')) return;
if (request.headers['x-admin-token'] !== config.adminToken) { /* 401 */ }
```

Fastify's router (find-my-way) percent-decodes the path **before** route matching, while
`request.url` keeps the raw form. A request whose first path segment is encoded therefore
reaches an `/api/...` handler without ever triggering the gate.

**Verified empirically** against a replica of the gate with find-my-way 9.9.0
(fastify 5.x):

```text
GET /api/admin/users            -> 401 unauthorized        (gate works)
GET /%61pi/admin/users          -> 200 <handler data>      (BYPASS — no token sent)
GET /api/admin/users + token    -> 200                     (control)
```

**Impact:** When the admin port is reachable by an attacker (non-loopback `ADMIN_HOST`,
container port mapping, exposed tunnel), **all** admin endpoints — delete any account,
remove devices, clear rate limits — are accessible without the token, even when
`ADMIN_TOKEN` is set.

</details>

### H2 — JWT falls back to a hardcoded dev secret

**Status: ✅ FIXED** — `be/src/config.js` + `be/src/server.js`. Added
`config.jwtSecretInsecure` (true when the secret is the dev default **or** shorter than
32 chars). `server.js start()` now throws before binding when the secret is insecure,
unless `ALLOW_DEV_JWT_SECRET=true`. `pnpm dev` sets that opt-out automatically
(loopback-only dev); the production path (`pnpm start`) does not. `.env.example`
documents `openssl rand -base64 48` for generating a real secret.

**Fix verified live:** booting without a real secret → hard error + no listener;
`ALLOW_DEV_JWT_SECRET=true` proceeds past the check.

<details>
<summary>Original finding</summary>

**Location:** `be/src/config.js:24` (`jwtSecret: env.JWT_SECRET ?? 'dev-secret-change-me'`)

If `JWT_SECRET` is unset, the server silently uses `'dev-secret-change-me'` (a
`console.warn` at startup is the only signal). Anyone who can reach the server can then
mint valid HS256 JWTs for **any** account and device (`{ sub, u, d }`) and use every
authenticated endpoint (`/api/me`, `/api/devices`, `/api/devices/approve`).

**Impact:** Full account takeover of every account when deployed without the env var.

</details>

### H3 — Vulnerable `@fastify/static` (path-traversal advisories)

**Status: ✅ FIXED** — `be/package.json`. Upgraded `@fastify/static` **8.3.0 → 10.1.3**,
which resolves all four advisories (including GHSA-8pvw-jcv7-9cmj, fixed only in
≥10.1.2). `pnpm audit` now reports **no known vulnerabilities**. Static-root adjacency to
`be/.env` remains, but the traversal vectors are closed.

**Fix verified live:** `/../.env`, `/%2e%2e/.env`, `/..%2f.env`, and double-encoded
variants on both the FE and admin static roots → 403/404 with **zero** secret bytes in
the response bodies.

<details>
<summary>Original finding</summary>

**Location:** `be/package.json` (`@fastify/static: ^8.0.0`), locked at **8.3.0**

`pnpm audit` reports **4 advisories, all on `@fastify/static@8.3.0`**:

| Advisory | Severity | Fixed in | Issue |
| -------- | -------- | -------- | ----- |
| GHSA-83w8-p2f5-377r | high | ≥10.1.1 | Route-guard bypass via path traversal |
| GHSA-x428-ghpx-8j92 | moderate | ≥9.1.1 | Route-guard bypass via encoded path separators |
| GHSA-pr96-94w5-mx2h | moderate | ≥9.1.1 | Path traversal in directory listing |
| GHSA-8pvw-jcv7-9cmj | moderate | ≥10.1.2 | Authorization bypass via non-canonical URL paths |

Both static registrations are exposed:

- **Main app** (`be/src/app.js`): serves `fe/`; `be/.env` (JWT secret, Mongo/Redis URLs,
  admin token) is one directory up — traversal that escapes the static root can reach it.
- **Admin app** (`be/src/admin.js`): serves `be/admin/`; `be/.env` is directly adjacent.

**Impact:** Potential disclosure of `be/.env` (→ JWT forgery, admin token, store
credentials) from the public port, depending on advisory mechanics.

</details>

### H4 — No session revocation — removed devices keep access

**Status: ✅ FIXED** — `be/src/app.js`. The bearer-token `onRequest` hook now re-checks
the token against the **live device registry** on every authenticated request: it loads
the account and confirms `request.auth.d` is still a registered device before setting
`request.auth`. A device removed by an admin loses access **immediately**, without
waiting for token expiry. This is revocation-by-registry (no blacklist needed). One extra
projected `findOne` per authenticated request — acceptable at MVP scale.

**Fix verified:** new regression test `admin device removal revokes the device session
(H4)` — a removed device's still-valid JWT is rejected on `/api/me` **and** blocked from
approving further devices, while the main device keeps working.

<details>
<summary>Original finding</summary>

**Locations:** `be/src/routes/shared.js` (`requireAuth`), `be/src/app.js:11-17`
(bearer hook), `be/src/routes/admin-routes/users.js` (device removal)

JWTs are stateless bearer tokens valid for `JWT_EXPIRES_IN_SEC` (default **24h**), and no
authenticated endpoint re-checks that `request.auth.d` is still a registered device on
the account. `requireAuth` only checks the token signature/expiry.

**Impact:**
- Admin-removing a device (`DELETE /api/admin/users/:username/devices/:deviceId`) does
  **not** revoke anything: the removed device's existing token keeps working on
  `/api/me`, `/api/devices`, and — notably — `/api/devices/approve`, so a compromised or
  stolen device can approve further devices for up to 24h after removal.
- There is no logout/revocation mechanism at all (FE "Log out" only drops its own copy).

</details>

## Medium

### M1 — Targeted login DoS via verify rate-limit exhaustion

**Status: ✅ FIXED** — `be/src/routes/app-routes/auth.js`. Reordered `/api/auth/verify`
to **consume the nonce first** and only count rate-limit attempts after a valid nonce is
presented, so junk requests can no longer drain a victim's budget. Also added a per-IP
verify budget (`rl:verifyip:<ip>`, `VERIFY_IP_LIMIT`) alongside the per-account one.

**Fix verified:** new regression test `verify junk cannot exhaust an account budget
(M1)` — 10 junk verifies with a budget of 3, then the victim still logs in successfully.

<details>
<summary>Original finding</summary>

**Location:** `be/src/routes/app-routes/auth.js:37-40`

The per-account counter `rl:verify:<ul>` is incremented **before** the nonce is checked,
and `/api/auth/verify` is unauthenticated. An attacker who knows a username can send 20
junk verify requests and exhaust the victim's budget (default 20/15 min), after which the
victim's legitimate logins receive `429` for up to 15 minutes. Repeatable indefinitely.

</details>

### M2 — Per-IP rate limiting collapses behind the production proxy

**Status: ✅ FIXED (code side)** — `be/src/config.js` + `be/src/app.js`. Added
`config.trustProxy` (parsed from `TRUST_PROXY`: `true`, a hop count, or comma-separated
trusted addresses) and passed it to Fastify, so `request.ip` reflects the real client IP
behind nginx. **Outstanding:** the actual nginx `X-Forwarded-For` configuration and a
staging check that `request.ip` is correct — see
[Outstanding items](#outstanding-items--follow-ups).

<details>
<summary>Original finding</summary>

**Location:** `be/src/app.js` (Fastify built without `trustProxy`); DESIGN.md deploys
nginx in front

Without `trustProxy`, `request.ip` behind nginx is the proxy's address for **every**
client. All IP-scoped limits (signup, challenge, device-enroll) then share one bucket:
a handful of requests from anywhere trip the limit for **all** users, while a distributed
attacker is equally "limited" — the protection inverts into self-DoS.

</details>

### M3 — Raw AES key bytes persisted in IndexedDB

**Status: ✅ FIXED** — `fe/js/app.js` + `fe/js/db.js`. Removed `aesRaw` from both
`saveIdentity` calls (signup and enroll) and from the documented record shape. Only the
non-exportable `aesEnc`/`aesMac` CryptoKey handles are stored, matching DESIGN.md and
`fe/README_TECH.md`. Nothing reads `aesRaw` back after the initial import.

<details>
<summary>Original finding</summary>

**Locations:** `fe/js/app.js:95-101` (signup) and `fe/js/app.js:265-267` (enroll) save
`aesRaw` into the identity record; `fe/js/db.js:28`

DESIGN.md and `fe/README_TECH.md` both state the AES key is re-imported as
**non-exportable** and the raw bytes are discarded ("the CryptoKey handles are the only
copies"). The code contradicted this: the raw base64url key bytes were stored in
IndexedDB and never read back after the initial import (login uses only the Ed25519 key
+ token).

**Impact:** Extractable transport-key material sat in IndexedDB indefinitely; any XSS
(see M4) or same-origin compromise could read it directly.

</details>

### M4 — No security headers (CSP, etc.)

**Status: ✅ FIXED** — `be/src/routes/shared.js` (`registerSecurityHeaders`), registered
in both `be/src/app.js` and `be/src/admin.js`. Every response now carries a strict
same-origin CSP (`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'
data:; connect-src 'self'; manifest-src 'self'; frame-ancestors 'none'; base-uri
'self'`), `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`. The
admin panel's inline `<style>` was moved to `be/admin/style.css` so the CSP can stay
strict (no `'unsafe-inline'`).

**Fix verified:** e2e check `security headers present (M4)` passes; CSP observed on the
live homepage.

<details>
<summary>Original finding</summary>

**Locations:** `be/src/app.js`, `be/src/admin.js` (fastify-static registered with no
headers)

Neither the FE nor the admin panel sent `Content-Security-Policy`,
`X-Content-Type-Options`, frame-protection, or `Referrer-Policy`. The FE holds key
material and session tokens, and the admin UI keeps the admin token in localStorage —
XSS in either context is maximally damaging, and CSP is the standard second line of
defense. The app is fully same-origin, so a strict CSP is cheap.

</details>

### M5 — `enrollId` capability leaks into server logs

**Status: ✅ FIXED** — `be/src/app.js`. Added a custom request-log serializer that
redacts the enroll-status path (`/api/devices/enroll-status/:redacted`), so the
unguessable capability never reaches stdout/log storage. Also added a generous per-IP
limiter on the endpoint (`rl:denrollstatus:<ip>`, default 600/15min) since it is
unauthenticated.

**Fix verified:** probed a fake capability and grepped the live logs — the raw value
appears **0** times; only the redacted path is logged.

<details>
<summary>Original finding</summary>

**Location:** `be/src/routes/app-routes/devices.js`
(`GET /api/devices/enroll-status/:enrollId`)

The enroll-status design relies on `enrollId` being an unguessable 192-bit capability.
But it travels in the URL path, and Fastify's default request logger logs the URL on
"request completed". Every poll writes the capability to stdout/log storage, weakening
the capability model whenever logs are collected, shipped, or shared.

</details>

### M6 — Signed payloads have no freshness (replayable)

**Status: ✅ FIXED** — `be/src/routes/app-routes/signup.js` + `devices.js`,
`be/src/routes/shared.js`, `fe/js/app.js`. Signed payloads (signup and device enroll)
now include a client timestamp `t` (epoch seconds) that must be within
`SIGNED_PAYLOAD_MAX_AGE_SEC` (default 5 min) of server time, **and** every accepted
signature is de-duplicated in Redis (`sigseen:<sha256>`, TTL `2 × max-age`), so a
captured payload cannot be replayed. The FE includes `t` in the canonical object it
signs. This establishes the pattern to carry into milestone-3 message envelopes.

**Fix verified:** regression tests for stale (`stale_payload`) and replayed (`replay`)
signup **and** enroll payloads.

<details>
<summary>Original finding</summary>

**Locations:** `be/src/routes/app-routes/signup.js`, `be/src/routes/app-routes/devices.js`
(signed object is `canonical({ a, d, p, u })`)

Signup/enroll signatures carried no nonce or timestamp, so a captured payload was valid
forever. Impact was limited today (signup is first-writer-wins; enroll replay only spawns
more pending codes, rate-limited per IP), but once milestone 3+ adds signed key-rotation
and message envelopes, replayable signed payloads become a direct threat.

</details>

### M7 — Admin API fails open without `ADMIN_TOKEN`

**Status: ✅ FIXED** — `be/src/admin.js`. Now **fail-closed**: a non-loopback
`ADMIN_HOST` with no `ADMIN_TOKEN` refuses to boot (`process.exit(1)`); loopback without
a token boots but logs a loud warning (local-dev convenience). Token comparison is
constant-time (SHA-256 + `timingSafeEqual`), and failed token attempts are throttled
per-IP (`rl:admintoken:<ip>`, 10/15min). `.env.example` marks the token as mandatory for
non-loopback binds.

**Fix verified live:** `ADMIN_HOST=10.0.0.5` with no token → refuses to boot.

<details>
<summary>Original finding</summary>

**Location:** `be/src/admin.js:16-21`

When `ADMIN_TOKEN` is empty the auth hook is **not registered at all**: user deletion,
device removal, and rate-limit clearing are open to anyone who can reach the admin port.
The 127.0.0.1 default bind mitigates local dev, but one misconfiguration
(`ADMIN_HOST=0.0.0.0`, Docker port mapping, an exposed tunnel) turns this into an
unauthenticated admin API. Secondary issues at the same spot:

- Token comparison uses `!==` (not constant-time) — timing leakage.
- No rate limiting on failed tokens — online brute force if the token is weak.

</details>

## Low

### L1 — Account/device enumeration

**Status: ✅ FIXED for challenge; ACCEPTED for signup/enroll.**
`be/src/routes/app-routes/auth.js`: `/api/auth/challenge` now issues a nonce for **any**
username/device pair (unknown pairs get a nonce that simply never verifies), so it no
longer reveals which accounts/devices exist. **Deliberately not changed:** `/api/signup`
still returns `409 username_taken` and `/api/devices/enroll` returns `404 unknown_account`
— both are needed for usable account-creation UX. Per-IP rate limits slow distributed
probing. Revisit if usernames become privacy-sensitive.

<details>
<summary>Original finding</summary>

`/api/auth/challenge` returns `404 unknown_account` vs a nonce; `/api/signup` returns
`409 username_taken`; `/api/devices/enroll` returns `404` for unknown accounts. These let
an attacker enumerate existing usernames and (username, device) pairs. Per-IP rate
limits slow this down but do not stop a distributed probe. Consider uniform responses
(e.g. challenge always succeeds but returns a nonce that will never verify for unknown
accounts/devices) once usernames become privacy-sensitive.

</details>

### L2 — Rate limiter INCR/EXPIRE race

**Status: ✅ FIXED** — `be/src/lib/rateLimit.js`. The counter is now created atomically
with its TTL (`SET key 0 NX EX window` followed by `INCR`), so a crash between the two
operations can no longer strand a key with no expiry (which would have rate-limited that
subject forever).

<details>
<summary>Original finding</summary>

**Location:** `be/src/lib/rateLimit.js:3-4`

`INCR` then `EXPIRE` on first hit: a crash between the two leaves the key with **no
TTL**, permanently rate-limiting that subject. Use a single atomic operation
(`SET key 1 NX EX window` + a separate counter, or a Lua script / `INCR` + check
`EXPIRE`'s result).

</details>

### L3 — Unbounded usernames + unvalidated rate-limit key subjects

**Status: ✅ FIXED** — `be/src/lib/username.js` (capped `USERNAME_RE` at `{5,64}`) and
`be/src/routes/app-routes/auth.js` (verify validates username/device format **before**
keying any rate-limit, so unauthenticated junk cannot create unbounded/arbitrary Redis
keys).

<details>
<summary>Original finding</summary>

- `USERNAME_RE` (`be/src/lib/username.js`) had **no upper bound**; only the FE enforced
  `maxlength="64"`. Server-side, a username up to the ~1MB body limit could be stored and
  echoed back. Cap at 64 chars.
- `/api/auth/verify` built `rl:verify:<u>` from the raw request value **before** any
  validation or existence check, so unauthenticated attackers could create unbounded
  distinct Redis keys (each TTL'd, but unbounded in number) with arbitrary characters.
  Validate format (and ideally account existence) before keying rate limits.

</details>

### L4 — Pairing-code collision overwrites a pending enrollment

**Status: ✅ FIXED** — `be/src/routes/app-routes/devices.js`. Pairing codes are now
claimed with `SET ... NX` and re-drawn on collision (up to 3 attempts, `503 enroll_busy`
if exhausted), so a second enrollment can never silently overwrite a first pending one.

<details>
<summary>Original finding</summary>

**Location:** `be/src/routes/app-routes/devices.js` (enroll `redis.set` of
`denroll:c:<ul>:<code>`)

Two enrollments on the same account could draw the same 6-digit code; the second `SET`
silently overwrites the first pending enrollment — the first device stalls until TTL.
Use `SET ... NX` and re-draw on collision, or key by `enrollId` with a code→enrollId
index.

</details>

### L5 — Admin rate-limit tooling misses milestone-2 limits

**Status: ✅ FIXED** — `be/src/routes/admin-routes/rateLimits.js`. `LIMIT_META` now covers
all counters (`verifyip`, `denroll`, `dapprove`, `dpending`, `denrollstatus`,
`admintoken`), so milestone-2 limits appear in `GET /api/admin/rate-limits`. Clear-by-IP
now removes **every** IP-scoped counter (`IP_SCOPED` list), not just signup+challenge.

<details>
<summary>Original finding</summary>

**Location:** `be/src/routes/admin-routes/rateLimits.js`

- `{ ip }` clear deleted only `rl:signup:<ip>` and `rl:challenge:<ip>`, not
  `rl:denroll:<ip>`.
- `LIMIT_META` had no `denroll`/`dapprove` entries, so those counters were filtered out
  of `GET /api/admin/rate-limits`.

Support could neither see nor clear device-enrollment limits.

</details>

### L6 — Device-approval UX is a social-engineering surface

**Status: ✅ FIXED** — new endpoint `POST /api/devices/pending` (JWT) in
`be/src/routes/app-routes/devices.js` returns the requesting device id + request time
without consuming the code; `fe/js/app.js` fetches it on approval and shows an explicit
confirmation dialog ("Device: 3aa52562… / Requested: <time> / Only approve if YOU just
started adding a device") before calling approve.

**Fix verified:** exercised end-to-end in a real browser (dialog shown → accept → device
list updated to 2/3).

<details>
<summary>Original finding</summary>

Anyone can start an enrollment against any existing account (it only proves nothing).
The approval gate is the user typing a 6-digit code — and the FE showed no details about
*what* they were approving. An attacker could present their own code to the victim
("approve this for me?"). Show the pending request's device id + request time in the
approve UI and require explicit confirmation; consider listing pending enrollments.

</details>

### L7 — Tokens in browser storage readable by XSS

**Status: ⚠️ MITIGATED (not eliminated).** No separate code change — the mitigation is
the strict CSP from [M4](#m4--no-security-headers-csp-etc) plus the existing XSS-free FE
(`textContent` only) and escaped admin UI. The underlying design (session JWT in
`sessionStorage`, admin token in `localStorage`) remains, which is standard for
token-based apps. Revisit if a higher-assurance session model is ever required.

<details>
<summary>Original finding</summary>

Session JWT in `sessionStorage` (`fe/js/app.js` `setToken`), admin token in
`localStorage` (`be/admin/app.js`). Standard for token-based apps, but combined with
M4 any XSS exfiltrates them. CSP plus keeping the FE XSS-free (it currently only uses
`textContent`; the admin UI escapes all interpolations) is the mitigation.

</details>

### L8 — JWT hardening gaps

**Status: ✅ FIXED (iss/aud); WS re-verify PENDING milestone 3.** `be/src/lib/jwt.js` now
issues and enforces pinned `iss` (`cocono-chat`) and `aud` (`cocono-chat-api`) claims.
The revocation story is covered by [H4](#h4--no-session-revocation--removed-devices-keep-access)
(live device-registry re-check on every request). When the WebSocket layer lands
(milestone 3), it must re-verify the JWT against the registry on connect/upgrade rather
than trusting it.

### Accepted design trade-offs
1. **L1 (signup/enroll enumeration)** — `/api/signup` `409 username_taken` and
   `/api/devices/enroll` `404 unknown_account` still reveal username existence, by design
   for usable account-creation UX. Revisit only if usernames become privacy-sensitive.
2. **L7 (tokens in browser storage)** — mitigated by CSP, but the token-in-storage model
   itself remains (standard for token-based apps). No `jti`/blacklist; revocation is
   registry-based (H4).

### Deployment-time checklist (operational, not yet done in code)
From DESIGN.md's deployment model (nginx TLS termination, pm2, self-hosted):

1. **TLS everywhere** — the app speaks plaintext HTTP by design (nginx terminates TLS);

   The boot check (H2) enforces this, but the real secret must actually be provisioned.

## What's already done well

- **JWT verification is sound:** `timingSafeEqual` MAC comparison, header pinned to the
  exact HS256 header (no `alg` substitution / `none` confusion), expiry enforced.
- **Login nonces:** 256-bit random, atomic single-use consumption via `GETDEL`, TTL'd —
  replays rejected (and regression-tested in `be/test/accounts.test.js`).
- **Race-safe writes:** unique index on `ul` handles concurrent signups; device approval
  uses an atomic `$push` guarded by `$expr` size check against `maxDevices`; pairing codes
  are per-account scoped, single-use via `GETDEL` (cross-account approval tested).
- **Strict input validation:** key lengths, charsets, base64url alphabet all checked
  server-side; the `enrollId` capability is 192-bit random.
- **Key hygiene in responses:** `/api/devices` and the admin user listing never expose
  `pub`/`aes` key material.
- **No DOM XSS surface in the FE** (only `textContent`); admin UI escapes every
  interpolated value.
- **Secrets hygiene:** `.env` gitignored (only `.env.example` committed); Mongo URL
  redacted in dev logs.
- **Rate limits exist on every sensitive endpoint** with `Retry-After`, and the test
  suite exercises replay, single-use, scoping, and limiting behavior.
