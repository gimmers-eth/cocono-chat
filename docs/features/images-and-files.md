## 2. Architecture summary (decisions already made — implement these)

1. **Transport split.** WS frames are capped at 64 KB (`MAX_FRAME_BYTES`), so
   blobs NEVER travel over the WebSocket. Media bytes move over **REST**
   (upload by sender, download by each recipient device). The *message* that
   references a blob rides the existing E2EE store-and-forward WS path, so
   delivery, ordering, idempotency, receipts and offline replay all keep
   working unchanged.
2. **Store-once semantics.** One upload = one server blob, regardless of how
   many recipient devices exist. The server keeps a `pending` set of recipient
   devices; the blob is deleted when every pending device has acknowledged
   download-or-decline (req 8), or after a retention sweep.
3. **Encryption.** Per-file random AES-GCM-256 key generated by the sender.
   Blob wire format = `iv(12) ‖ ciphertext ‖ tag(16)` (same shape as message
   ciphertexts). The key + metadata travel **inside the per-device envelope
   ciphertext** — a "media message" is a JSON payload in `m.d`, exactly like
   existing `{"sys":...}` messages. The server never sees the key, filename or
   mime type; it only sees routing metadata it already sees today plus a small
   plaintext attachment descriptor (§3.2).
4. **Server blob storage.** MongoDB `media` collection with `Binary` fields
   (precedent: avatars in `profiles`, ID docs in `id_docs`). A 10 MB blob fits
   the 16 MB doc limit with headroom. If the size cap is ever raised, move to
   GridFS behind the same route module — do not do that now.
   **DEVIATION (reports):** a report's DECRYPTED attachments cannot live on the
   report doc — three 10 MB items blow through Mongo's 16 MB document limit —
   so they are one doc each in `report_media`, keyed `{report, index}`, served
   by the admin and deleted with the report.
5. **Thumbnails.** The server cannot render ciphertext, so the CLIENT generates
   a small thumbnail (images: 256 px JPEG; videos: poster frame from a
   `<video>` + canvas capture) and encrypts it under the SAME file key with its
   own IV. Thumbnails power chat bubbles, the image wall and video posters
   without downloading full blobs.
6. **Auto-download policy.** Images (incl. thumbnails-only for videos) are
   auto-downloaded on receipt; video full bytes and files are manual
   (download / decline buttons). Blur default follows the sender's
   admin-`verified` flag (req 7).

## 3. Wire format & data model

### 3.1 The media message payload (inside the E2EE envelope `m.d`)

Plaintext is a JSON string (same channel as `{"sys":...}`; distinguished by the
`media` key — see §6.3 for parsing order in the app):

```json
{
  "media": {
    "id":   "<server blob id returned by POST /api/media>",
    "kind": "image" | "video" | "file",
    "mime": "image/jpeg",
    "name": "holiday.jpg",              // sanitised by sender, never trusted by receiver
    "size": 183402,                     // plaintext byte size
    "key":  "<b64u AES-GCM-256 key>",
    "iv":   "<b64u 12-byte IV for the full blob>",
    "thumbIv": "<b64u 12-byte IV for the thumbnail>",  // present when a thumb exists
    "sha256": "<b64u SHA-256 of the CIPHERTEXT blob>", // integrity check after download
    "w": 1600, "h": 1200,               // images/videos only (thumb-scaled ok for videos)
    "dur": 12.4,                        // videos only, seconds
    "animated": true                    // images only: GIF/animated WebP (drives play/pause control)
  }
}
```

The key is identical in every device copy (the envelope ciphertext differs per
device as today; only the *envelope* is per-device-pair encrypted).

**Outgoing multi-device sync** (see `docs/features/outgoing-multidevice-sync.md`,
built first): the sender's OTHER own devices receive the same media object
wrapped in the sync payload —
`{"sync":1,"id":"<localId>","peer":"<recipient>","ts":<ms>,"media":{...}}` —
with the envelope's plaintext `sync:1` flag. They store it as a `dir:'out'`
record under the same `out:<localId>` id and participate in the blob lifecycle
like any recipient device (§4.3).

### 3.2 Envelope extension — plaintext attachment descriptor

`m` gains ONE optional field (server-visible routing metadata; covered by the
existing HMAC `h`, so it cannot be tampered with):

```json
"att": { "id": "<blob id>", "kind": "image|video|file", "size": 183402 }
```

Sync copies to the sender's own devices carry the same `att` PLUS the
plaintext `"sync": 1` flag defined in the outgoing-sync plan (server: no
push, no counter; `att` bookkeeping is identical — own devices land in
`devices`/`pending` too).

Why plaintext: the server must manage blob lifecycle (which devices still owe
an ack, when to delete — req 8) without decrypting anything. `size` here is the
CIPHERTEXT size; it must match the stored blob. Validation rules in §4.2.

`be/src/routes/ws-routes/envelope.js` validation: `att` optional; when present
all three fields required, `kind` in enum, `id` matches `^[a-zA-Z0-9_-]{8,64}$`,
`size` a positive integer ≤ cap. Anything else → `invalid_envelope`.

### 3.3 Server `media` collection (new, `be/src/db.js` index setup)

```javascript
{
  _id: <blob id, server-generated uuid>,
  owner: { ul, fd },              // uploading device — the sender
  kind: 'image' | 'video' | 'file',
  ctSize: <number>,               // ciphertext blob byte length
  thumbCtSize: <number|null>,
  sha256: <b64u of ciphertext>,   // as claimed by uploader (see §4.2 note)
  blob: Binary,                   // iv‖ct‖tag, encrypted — server cannot read
  thumb: Binary | null,           // encrypted thumbnail
  devices: [ { ul, dv } ],        // authorised recipients (added by handleSend)
  pending: [ { ul, dv } ],        // devices that have NOT yet acked (§4.3)
  reported: false,                // pinned by a report — excluded from deletion (§7)
  ts: Date                        // upload time (retention sweep sorts on this)
}
```

Indexes: `{ 'owner.ul': 1 }`, `{ ts: 1 }`. No unique constraint on sha256
(cross-send dedup is deliberately NOT done: keys differ per send, and hash
matching would create an upload oracle).

### 3.4 Client IndexedDB (app store, `client/app/js/store.js`)

Bump `DB_VERSION` 5 → 6. New store **`media`**, keyPath `id` (= blob id):

```javascript
{
  id, peer, dir: 'in' | 'out', kind, name, mime, size,
  key, iv, thumbIv, sha256, w, h, dur, animated,   // from the media payload
  state: 'pending' | 'downloading' | 'stored' | 'declined' | 'expired' | 'failed' | 'pruned',
  keep: false,                    // pin against local pruning (§4.5) — 'Keep' toggle in the viewer
  blurred: true | false | null,   // null = no override, use the verified-flag default (§6.7)
  data: Blob | null,              // DECRYPTED full bytes (null until downloaded / after decline)
  thumb: Blob | null,             // DECRYPTED thumbnail (images/videos)
  msgId, ts                       // link to the transcript record
}
```

Message records (`messages` store) gain `kind: 'text'|'image'|'video'|'file'`
and `mediaId` so tabs can query the transcript without joining. Sender side:
the record + `media` row (with `data` = plaintext Blob) are written BEFORE
upload starts, which is what satisfies "the sender has a local copy" (req 4)
even if the send fails.

## 4. Backend work

New route module `be/src/routes/app-routes/media.js`, registered in
`app-routes/index.js` like the others (JWT via `requireAuth`, limiter pattern
copied from `profile.js` / `reports.js`).

### 4.1 REST endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/media` | sender uploads ciphertext blob (+ optional encrypted thumb) |
| GET | `/api/media/:id` | an authorised recipient device downloads the ciphertext |
| POST | `/api/media/:id/ack` | device confirms download OR decline → lifecycle step |

**POST /api/media** — JSON body (base64 is fine here; the 33 % expansion is
absorbed by the bodyLimit):

```json
{ "kind": "image", "blob": "<b64u iv‖ct‖tag>", "thumb": "<b64u | null>", "sha256": "<b64u>" }
```

- `bodyLimit`: `mediaMaxBytes * 1.4 + 64 KB` (same trick as the ID-doc route).
- Auth: JWT; device must be registered (existing `requireAuth` semantics).
- Limits: ciphertext ≤ `MEDIA_MAX_BYTES` (10 MB), thumb ≤ `MEDIA_THUMB_MAX_BYTES`
  (64 KB); rate limiters `mediaup` per IP + per account; **per-account quota**:
  sum of `ctSize` over non-deleted docs owned by the account ≤
  `MEDIA_QUOTA_MB` (default 100) → 413 `media_quota`. This is the media half
  of the P0 "queue DoS" concern — do not ship without it.
- The server CANNOT validate mime/magic bytes (ciphertext) — that is fine and
  by design; it stores `kind` (enum-checked) and the claimed `sha256`.
- Response: `{ id }`.

**GET /api/media/:id** — allowed only when `(auth.sub, auth.d)` appears in the
doc's `devices` array (the sender may also fetch their own upload until it is
deleted, useful for retry flows). Returns raw bytes
(`content-type: application/octet-stream` — NEVER a browser-renderable mime
from our origin; existing CSP + `nosniff` stay load-bearing) with headers
`x-cocono-kind` and ETag = sha256. 404 `unknown_media` when missing/deleted —
do not distinguish "exists but not yours" from "gone" (enumeration care).
Rate limiter `mediadl` per IP + account.

**POST /api/media/:id/ack** — body `{ "downloaded": true | false }`. Removes
the caller's `{ul,dv}` from `pending` (only devices in `devices` may ack;
acks are idempotent). Triggers the deletion check (§4.3). `downloaded:false`
is the "delete before downloading" path (req 6). Response `{ ok, deleted }`.

### 4.2 `handleSend` changes (`be/src/routes/ws-routes/handlers.js`)

After the existing validation chain, when `m.att` is present:

1. Load the media doc; require it exists, is not `reported`-pinned-deleted,
   `owner.ul === m.f` and `owner.fd === m.fd` → else ack `unknown_attachment`
   (new error code; add to the §2.9 table in MESSAGES.md).
2. Require `att.kind === doc.kind` and `att.size === doc.ctSize` → else
   `invalid_envelope`. (The HMAC makes `att` sender-authenticated; these checks
   stop a sender corrupting their own lifecycle bookkeeping.)
3. `$addToSet` the recipient `{ul: m.u, dv: m.dv}` into BOTH `devices` and
   `pending` (idempotent under cid-retries and multi-copy fan-out).
4. Persist the message doc exactly as today. The `att` lives inside `env` — no
   schema change to `messages`.

Nothing else in the WS layer changes: `pulled`, `delivered`, receipts, push
gating and resync all keep working because a media message IS a message.

### 4.3 Lifecycle & deletion (req 8)

- After every ack, if `pending` is empty and `reported === false`:
  `deleteOne` the doc (blob gone — "downloaded on all devices ⇒ remove").
  Deletion is best-effort inline; a sweeper (below) is the safety net.
- **Sweeper** (add to whatever periodic hook the planned undelivered-message
  sweep uses; if none exists yet, a `setInterval` in `server.js` behind the
  existing single-process assumption, hourly): delete media docs with
  `ts` older than `MEDIA_RETENTION_DAYS` (default 7) and not `reported`.
  Also delete orphan uploads: docs whose `devices` is still empty after
  24 h (uploaded, never sent — crashed client).
**Implemented:** `sweepMedia()` runs hourly from `server.js`
(`startMediaSweeper`, `MEDIA_SWEEP_SEC`), and — as the plan requires — the
account-purge path (`deleteAccountFully`) deletes the account's owned blobs.
`ops/wipe-data.sh` auto-discovers `media` and `report_media` (verified: neither
is on the KEEP list, so a dev reset drops both).

- **Resync/replay consequence:** once a blob is deleted, a device that later
  replays the envelope (resync, or a second device pulling late — impossible
  today since pending covers all devices, but keep the code honest) gets 404
  from GET; the app marks the media record `expired` and renders a "no longer
  available" placeholder. Do NOT hold blobs for deleted-message retries.
- Account deletion (all three paths) and `ops/wipe-data.sh`: `media` is a
  user-keyed collection, auto-discovered by the wipe script (no KEEP-list
  edit needed — verify only). Account purge must delete the account's owned
  media docs (mirror what `profiles`/`id_docs` purge does).

### 4.5 Pruning — time bounds for messages, files and images

Everything this feature stores gets a time bound; nothing lives forever:

| What | Where | Bound | Mechanism |
|---|---|---|---|
| Undelivered message copies (incl. media envelopes + sync copies) | server `messages` | `MSG_QUEUE_MAX_DAYS` (default 30) | `expireAt` stamped at insert + TTL index — shipped by the outgoing-sync branch, media inherits it for free |
| Pulled message copies | server `messages` | `MSG_RETENTION_SEC` (existing, 30 d) | existing TTL (resync window) |
| Media blobs not yet acked by all devices | server `media` | `MEDIA_RETENTION_DAYS` (default 7) | sweeper (§4.3); orphans (never-sent uploads) after 24 h |
| Media blobs acked by all devices | server `media` | immediate | delete-on-empty-pending (§4.3), `reported` docs pinned (§7) |
| Decrypted media bytes on a device | client IDB `media` | `MEDIA_LOCAL_RETENTION_DAYS` (default 7, settings drawer) | **IMPLEMENTED with one correction:** the window is measured from `storedAt` (when the bytes ARRIVED on this device), not from `ts`. Reading `ts` made manual downloads meaningless — open a three-week-old chat, Download a file, and the next pass drops the bytes the user just waited for, possibly for good. Prune job at app boot + daily interval: for `state:'stored'` records older than the window and `keep !== true`, drop `data` (and `thumb` only for files — images/videos KEEP the thumb), set `state:'pruned'`. Records/transcript rows stay (name, size, date, direction); viewer shows thumb-or-icon + "Removed from this device". `keep` is toggled by a **Keep** button in the media modal (§6.4) — DESIGN.md's "mark to keep long term". **IMPLEMENTED with a second correction:** the plan's "re-download is impossible" is only knowable by the SERVER, so a pruned row must not claim it — it offers **Download again** and takes the 404 as the answer when the copy really is gone (`pruned` ≠ `expired`: one is this device letting bytes go, the other is proof nothing is left). The confirm copy that survives is the true one: the server usually HAS deleted it, because downloading is what acks it. |
| Text transcripts on a device | client IDB `messages` | none (local user history) | deliberately NOT pruned locally — the server's copies are; the device transcript is the user's own data (clear-chat remains manual) |

### 4.4 Config (`be/src/config.js` + `.env.example`)

**DEVIATION (minor, deliberate):** uploads also verify the claimed `sha256`
against the bytes server-side (`400 bad_sha256`). The plan stored "the claimed
sha256"; a stored digest that lies would poison the ETag and every later
integrity check, and verifying costs one hash pass over a ≤10 MB buffer.

**DEVIATION (client IDB):** an OUTGOING media row is keyed by the sender's own
record id with the server blob id in a separate `blobId` field, because the row
is written BEFORE the upload returns an id (req 4). Every wire call goes through
`blobOf(row)` and refuses politely when it is null; incoming rows keep the
plan's keyPath (the blob id itself).

```
MEDIA_MAX_BYTES            (default 10 * 1024 * 1024)   — ciphertext cap, all kinds
MEDIA_THUMB_MAX_BYTES      (default 64 * 1024)
MEDIA_QUOTA_MB             (default 100)                — per account, server-held bytes
MEDIA_RETENTION_DAYS       (default 7)                  — un-acked sweep
MEDIA_UP_IP_LIMIT / MEDIA_UP_ACCOUNT_LIMIT              — e.g. 60 / 60 per 15 min
MEDIA_DL_IP_LIMIT / MEDIA_DL_ACCOUNT_LIMIT              — e.g. 240 / 240 per 15 min
```

Register the new limiters in the limits catalog (`be/src/lib/limits.js` +
admin Traffic page registry) so per-user/IP overrides and the "clear limits
for IP" sweep cover them like every other limiter.

## 5. SDK work (`client/src/`)

### 5.1 `api.js`

`uploadMedia(token, {kind, blob, thumb, sha256})`, `downloadMediaRaw(token, id)`
(returns `ArrayBuffer`, throws `CoconoApiError('unknown_media')` on 404),
`ackMedia(token, id, downloaded)`.

### 5.2 `client.js`

- **`async sendMedia(username, { kind, file, name, thumb })`** — the app does
  resizing/thumbnailing/UI; the SDK does crypto + transport (keep that split —
  the SDK has no DOM):
  1. Generate a random AES-GCM-256 key + IV; encrypt bytes; SHA-256 the
     ciphertext; encrypt thumb under the same key with its own IV.
  2. `POST /api/media` → `{ id }`.
  3. Fan out exactly like `sendMessage`: per recipient device, envelope with
     `d` = encrypted JSON media payload (§3.1), `att` = `{id, kind, size:
     ctSize}`, per-device `cid`, HMAC. Reuse `#getConvKey`, `#cidToLocal`,
     ack/delivered events — a media send reports progress through the SAME
     `ack`/`delivered` events keyed by the returned `localId`.
  4. **Sync fan-out to own other devices** (outgoing multi-device sync):
     same `sync:1` envelopes as text, payload `{"sync":1, id, peer, ts,
     media:{...}}`, sync cids tracked in `#syncCids` (never flip bubble
     state). The plaintext `att` rides along so `handleSend` registers the
     own devices in `devices`/`pending` — they owe a download+ack before the
     blob may be deleted.
  5. Upload failure → throw before any envelope goes out (nothing half-sent);
     envelope failure after upload → the orphan sweeper reclaims the blob.
- **Receive path (`#onIncoming`)** — unchanged plumbing: it already emits
  `{ text }`; the app parses the `media` JSON. The SDK does NOT auto-download
  (policy lives in the app), but expose:
  - `downloadMedia(id, { key, iv, thumbIv, sha256 })` → fetch, verify sha256
    of ciphertext, decrypt, return `{ data: Blob, thumb: Blob|null }`.
  - `ackMedia(id, downloaded)`.
- **Self-chat:** media to your own username behaves like text (echo is pulled,
  not re-saved); the local copy already exists.

### 5.3 `crypto.js`

Add `encryptBytes(key, ArrayBuffer) → iv‖ct‖tag` / `decryptBytes` helpers (the
string variants are just these + utf8; refactor so both share one path) and a
`sha256B64u(bytes)` helper.

### 5.4 Push worker (`client/app/sw.js` / `sw-lib.js`)

The blind push payload needs NO change (event-type only). The worker's
silent-resume peek decrypts envelopes; teach its notification-text builder to
recognise the `media` payload and render "Photo" / "Video" / "File: <name>"
instead of raw JSON — the worker must NOT download blobs (battery/data); it has
everything it needs from the decrypted payload. Check all THREE notification
emitters (skill rule): server push gate (unchanged — a media message is a
message), page-level `notifyOS` in chat.js, and worker banners.

### 6.3 Send pipeline + bubble rendering (req 3, 5)

Client-side preparation BEFORE calling `client.sendMedia` (new module
`client/app/js/media.js` — keep chat.js from growing another 500 lines):

- **Kind detection** from mime: `image/*` → image, `video/*` → video, else
  file. **Reject `image/svg+xml` outright** (script-bearing format; our origin
  must never render one) with a clear toast.
- **Image resizing (req 5):** static JPEG/PNG/WebP → canvas downscale to
  longest edge ≤ 1600 px, re-encode JPEG q≈0.85 (keep PNG when it has alpha
  and is already small); phone photos never hit the wire at full size (same
  philosophy as profile avatars). Animated GIF/WebP: do NOT re-encode
  (canvas kills animation); pass through if ≤ `MEDIA_MAX_BYTES`, else refuse.
- **Videos:** no transcoding (out of scope); refuse if > 10 MB with a toast
  explaining the limit. Poster thumb via `video.currentTime = 0` + canvas
  `drawImage` (needs the local File as an object URL; best-effort — send
  without thumb if capture fails).
- **Files:** refuse > 10 MB. Sanitise the name (strip any path components,
  collapse whitespace, cap length ~120).
- Thumbnails for all kinds: 256 px longest edge JPEG q≈0.7, ≤ 64 KB encrypted.

Transcript record: extend `saveMessage` usage with `kind` + `mediaId`; render
bubbles by kind in chat.js:

- image → inline `<img>` from the decrypted thumb Blob (object URL), max
  bubble width; blurred via CSS `filter: blur(...)` when the blur policy says
  so (§6.7).
- video → poster thumb + centred play badge (+ duration chip).
- file → icon + name + size + state row (Download / Decline buttons when
  `state: 'pending'`; progress/status otherwise).
- outgoing media → thumb/icon + the normal state marks (sending ✓ ✗ ✓✓);
  show an upload progress affordance (determinate if fetch progress is
  available, else the existing `stateSending` clock) while `POST /api/media`
  runs. Failed sends reuse the existing failed-bubble affordance.
- Object URLs: create lazily, revoke on re-render/close (no URL leaks across
  the render-loop — chat.js re-renders often).

### 6.4 Message modal / viewer controls (req 3, 7)

Extend the existing `#msg-modal` (it already survives `render()` and has the
Copy/Forward/Delete action row):

- For media messages the scrollable text area is replaced by a media pane:
  - **image:** full decrypted image (object URL). Controls row: Blur/Unblur
    toggle (eye icons), and for `animated: true` a Play/Pause toggle —
    implement pause by swapping `src` to the static thumb (or a first-frame
    canvas capture); resume swaps back to the animated Blob URL. Native GIF
    playback cannot be paused in an `<img>`, do not fight it.
  - **video:** `<video>` element (Blob URL, `playsinline`, NO `controls` —
    custom row matches the app): Play/Pause, Mute/Unmute, Blur/Unblur
    (CSS filter on the element). If `state !== 'stored'`, the pane shows the
    poster + a Download button instead.
  - **file:** name/size + Download button (`a[download]` + Blob URL → saves
    the decrypted bytes under the original name).
    **IMPLEMENTED, widened:** every stored item (image/video/file) gets
    **Save to device**, which prefers `navigator.share({files})` — the door
    that actually works in an installed PWA on iOS/Android — and falls back to
    `a[download]` + Blob URL with a filename that always carries an extension
    (`deviceFileName`), then SAYS which door it used. Images also get **Expand**
    (full-size lightbox, rectangular).
- Copy is hidden for media; **Forward** re-sends via `sendMedia` using the
  locally stored plaintext (fresh key, fresh upload — never forward a blob
  id); **Delete** removes the local transcript + media records only (server
  copy lifecycle is the ack/sweeper's job).
- Blurred-by-default images: the blur is a RENDER state over already-decrypted
  data (req 7 is about display, not download). The toggle writes `blurred`
  into the IDB `media` record so it persists.
- **Keep** toggle (all kinds): pins/unpins the local decrypted copy against
  the pruning job (§4.5); writes `keep` into the `media` record; label states
  honestly ("Keep on this device" / "Kept").

### 6.5 Tabs data source

Images/Videos/Files tabs query the transcript (`byPeer` index) filtered by
`kind`, joined against the `media` store for state/thumb. Sent vs received =
`dir`. Everything is device-local — no server calls (consistent with the
message-actions/clear-chat model).

### 6.6 Receive pipeline (req 6)

In `main.js`'s `client.on('message')` handler, BEFORE the sys-message check,
detect `/^\{"media":/` payloads (defensive `JSON.parse` in try/catch like the
sys path; unparsable → treat as plain text):

1. Save the transcript record (`kind`, `mediaId`) + a `media` IDB row
   (`state: 'pending'`).
2. **Images:** auto-download → `client.downloadMedia(...)` → verify sha256 →
   store decrypted `data` + `thumb`, `state: 'stored'` → `client.ackMedia(id,
   true)`. On failure (offline, 404 `expired`): set `failed`/`expired`, still
   ACK `true` for 404s (the blob is gone; holding pending blocks req 8
   forever) and retry `failed` ones on the next `open` event (small retry
   queue; do not hammer — respect the download limiter).
3. **Videos:** auto-download the THUMB only — add `GET /api/media/:id?part=thumb`
   (returns just the thumb bytes; same authorisation) so posters appear
   without pulling 10 MB. Full bytes stay `pending` behind the Download
   button; ack only after full download or decline. (Thumb-only fetch does
   NOT ack.)
4. **Files:** stay `pending`. Bubble shows Download and Delete ("decline")
   buttons. Decline → `client.ackMedia(id, false)`, `state: 'declined'`,
   bubble collapses to a "deleted" row — this is req 6's "delete before
   downloading marks it as received".
5. Images ack immediately after successful store (req: images auto-download;
   acking promptly is what lets the server delete — req 8).
5a. **A poster fetch is decoration** (found on device): a video sent without a
    thumbnail (`videoPoster()` failing is normal on iOS) made the recipient's
    `?part=thumb` GET return the same 404 as a swept blob, the app read that as
    'expired', acked it — and the ack DELETED the video for every device. Now
    the server answers `404 no_thumb` for a listed caller whose blob simply has
    no preview, and `applyArrivalPolicy` never touches `state` or the ack on a
    poster path. Rule: **only a payload fetch may settle the lifecycle.**
6. **Sync copies (own other devices):** the SDK's `sync` event (§5.2 step 4)
   carries the media payload; the app stores the transcript record as
   `dir:'out'`, `state:'synced'` + a `media` row, and applies the SAME
   download policy (images auto-download+ack; videos thumb-only; files wait
   for the user). No notifications of any kind for sync arrivals (three-
   emitter rule — see the outgoing-sync plan §2.5).

### 6.7 Blur policy (req 7)

Default blur for RECEIVED images when the sender is not identity-verified:
read the `verified` flag from the per-account IDB `peers` store (already
cached from `peerKeys`; DB v4). `verified === true` → unblurred; anything else
(false/unknown) → blurred. Applies to bubbles, wall tiles and the viewer's
initial state; the user's explicit toggle (`blurred` override) wins. Sent
images are never blurred. Re-check on `peerIdentityChanged`-style notice
events is NOT needed — the flag is read at render time.

## 7. Reports — server-decryptable media (req 9)

Current model (`be/src/routes/app-routes/reports.js`): the reporter's client
hands the server plaintext transcript. Extend it:

- Client: `reportUserWithConfirm` includes, for media messages in the
  reported conversation, an entry per item:
  `{ blobId, key, iv, thumbIv?, name, mime, kind, data? }` — `key/iv` come
  from the local `media` record; `data` (b64 PLAINTEXT) is included ONLY when
  the server no longer holds the blob (the client knows: it got a 404 on
  download, or simply always includes data for items it has locally — decision
  for the implementer: prefer keys-only when the blob is server-resident to
  keep reports small, include bytes when not).
- Server: on report intake, for each media entry — if the blob still exists,
  set `reported: true` on the media doc (pins it against §4.3 deletion) and
  decrypt it with the supplied key, storing the PLAINTEXT bytes on the report
  doc (moderation records are kept until an admin deletes them; cap total
  report media at e.g. 3 items / 30 MB, raise the route `bodyLimit`
  accordingly). If the blob is gone, store the client-supplied `data`.
  Decrypt failures (bad key) store the entry with an `undecryptable` flag —
  never fail the whole report because of one item.
- Admin panel (`admin/app.js` + `admin-routes/reports.js`): render report
  media — images inline, video with a player, files as a download link
  (admin is loopback-only and already uses innerHTML with escaping; serve
  media bytes through an admin route, not by pointing at `/api/media`).
- The privacy warning shown before sending a report must mention that
  attached photos/videos/files from the conversation are shared in readable
  form.

## 8. Security & abuse checklist (review before merge)

- [x] Blob bytes only ever served as `application/octet-stream` + `nosniff`
      from our origin; NO user-controlled content-type; SVG refused at pick
      time AND rejected by the viewer if it ever appears.
- [x] GET/ack authorisation is exactly `(ul,dv) ∈ devices` — no username-only
      access (a second device of the recipient must have received its own
      envelope copy to be in `devices`).
- [x] sha256 verified client-side after download; mismatch → treat as failed,
      do not store, do not ack `true` (but DO surface an error — a lying
      server should be visible).
- [x] Quota + retention + orphan sweep all shipped in the same PR as upload
      (unbounded blob storage is a P0-class DoS).
- [x] New limiters registered in the limits catalog (`mediaup`,
      `mediaupacct`, `mediadl`, `mediadlacct` — labels, per-account overrides
      and the 'clear limits for IP' sweep all cover them, asserted in
      `be/test/media.test.js`); kill-switch (`traffic`) behaviour unchanged.
- [x] Filename/mime from the envelope are untrusted input at render time
      (textContent only — the no-innerHTML rule already forces this).
- [x] `att` cannot reference someone else's blob (owner check) or forge kind/
      size (HMAC + doc comparison).
- [x] Account purge and `ops/wipe-data.sh` handle `media` (auto-discovery
      should cover it — verify, don't assume).
- [x] Push payloads remain blind (no kind/name leaks into FCM/APNs) — the send
      seam pushes `('msg', sender)` exactly as for text; the page and the worker
      label media locally from the decrypted descriptor.
- [x] CSP untouched; no new remote origins; Blob URLs only.

## 9. Known gaps / accepted behaviour (document, don't fix here)

- Outgoing media sync covers messages sent while the sender's other devices
  already exist; NEW devices get no backfill (same gap as text — see
  `docs/features/outgoing-multidevice-sync.md` §1).
- Once all devices ack, the blob is gone: resync/reinstall cannot restore
  media (`expired` placeholder). This mirrors message retention semantics.
- No streaming/range support — ≤10 MB blobs are downloaded whole. Fine for
  the cap; revisit with GridFS + Range if the cap ever grows.
- Video transcoding/compression is client-out-of-scope; a 10 MB cap on video
  is short — accepted for M4 (DESIGN.md keeps richer media post-MVP).
